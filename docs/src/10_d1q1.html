2. Les branches main et develop

Le modèle retenu est un Git Flow simplifié, adapté à une équipe Scrum qui livre en production à chaque fin de sprint (Bloc 2) mais doit pouvoir corriger la production entre deux sprints :

  • main ne contient que du code livré : chaque commit de main est une version étiquetée (v1.0.0) et déployée ;
  • develop intègre en continu les fonctionnalités terminées du sprint ; elle est toujours déployable sur l’environnement de recette ;
  • chaque User Story ou correction vit dans une branche courte créée depuis develop et fusionnée sans avance rapide (--no-ff), ce qui garde la trace de la branche dans l’historique ;
  • une version passe par release/X.Y.Z (stabilisation, documentation), est fusionnée dans main, étiquetée, puis refusionnée dans develop ; un correctif urgent part de main dans hotfix/* et revient dans les deux.

J’ai choisi ce modèle plutôt que le trunk-based development parce que deux contraintes du contexte imposent une branche de production stable distincte de l’intégration : les jalons réglementaires (analyse d’impact RGPD, comité go / no-go du Bloc 2) et la coexistence prolongée des applications historiques. Le trunk-based conviendrait à une équipe qui déploie plusieurs fois par jour derrière des feature flags, ce qui n’est pas le cas ici.

3. La convention de nommage des branches

La convention est documentée dans CONTRIBUTING.md et, surtout, appliquée par un script (scripts/check_branch_name.py) que la CI exécute à chaque push et que le hook pre-commit lance en local. Une convention seulement écrite finit toujours par être contournée.

<type>/<ticket>-<description-courte>

type        feature | fix | hotfix | docs | ci | chore | test | refactor     (release : release/X.Y.Z)
ticket      FUS-<n>  — identifiant du ticket du backlog (projet « Fusion »)
description 2 à 6 mots en kebab-case, minuscules, sans accent

^(main|develop)$
|^(feature|fix|hotfix|docs|ci|chore|test|refactor)/FUS-[0-9]+-[a-z0-9]+(-[a-z0-9]+){1,5}$
|^release/[0-9]+\.[0-9]+\.[0-9]+$
ExempleRésultatPourquoi
feature/FUS-4-bus-kafka-extractionconformetype, ticket et description explicites
fix/FUS-9-paiements-comptes-deux-foisconformela description dit le symptôme, pas la solution
release/1.0.0conformeversion sémantique, sans ticket
feature/dashboardrefuséeticket absent : impossible de relier le code à la User Story
Feature/FUS-4-Busrefuséemajuscules (problèmes de casse entre Windows et Linux)
fix/FUS-12-correctifrefuséedescription d’un seul mot, trop vague

Le préfixe de ticket relie chaque branche au backlog Trello du Bloc 2 ; le type permet de filtrer l’historique (toutes les corrections : git log --grep "^fix") et de déclencher des règles de CI différentes. Les messages de commit suivent la même logique avec les Conventional Commits en français (feat(silver): …, fix(silver): …, Refs: FUS-9).

4. Règles de protection et de fusion

  • Pas de push direct sur main ni develop : fusion par pull request uniquement, une revue obligatoire pour main.
  • CI verte obligatoire avant fusion : convention de branche, ruff (lint et format), bandit, tests sur trois versions de Python avec un seuil de couverture de 85 %, jobs Spark, intégration Kafka, recette de l’image Docker.
  • Une correction commence par un test qui reproduit l’anomalie. L’historique de fix/FUS-9 le montre : un commit de tests rouges, puis le commit du correctif.
