Question 2. Faites des tests unitaires et montrez votre test coverage.

C3.3 — Critère : pratiques de test et de validation des correctifs.

1. Stratégie

Les tests suivent la pyramide habituelle : beaucoup de tests unitaires rapides sur les règles, moins de tests d’intégration sur l’enchaînement, quelques tests de bout en bout sur le pipeline et l’application. Trois principes :

  • Chaque règle de nettoyage est testée sur ses cas limites réels, ceux rencontrés au profilage : 31/02/1985, 1900-01-01, +33 (0)6…, un mobile belge, un nom en capitales placé avant le prénom. Les tests sont paramétrés (pytest.mark.parametrize) : un cas par ligne, lisible comme une table de spécification.
  • Les tests portent sur le comportement, pas sur l’implémentation. Par exemple : « un message non validé est relivré », « une ligne republiée ne double pas le silver », « un utilisateur reçoit 403 sur la route qualité ».
  • Les données de test sont générées, déterministes et petites : le générateur produit un jeu au 1/20e en une fraction de seconde, une seule fois par session de tests. La suite complète s’exécute en une quinzaine de secondes.

Les tests Spark et Kafka sont marqués (-m spark, -m kafka). Ils s’exécutent dans la CI, qui fournit une JVM et un broker ; sur un poste qui n’en dispose pas, ils sont ignorés proprement au lieu d’échouer.
