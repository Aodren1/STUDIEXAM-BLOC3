1. Le pipeline réalisé

Le pipeline suit à la lettre l’architecture cible de l’énoncé (BDD X Oracle / BDD Y SQL Server → Talend → Kafka → Talend/Spark → Hadoop → Dataviz), avec une zone de données par étape :

2. Contrat des messages et organisation du lac

Enveloppe d’un événement (topic src.ap.client)

{"schema": "fusion.src.v1", "op": "r",
 "ts_ms": 1795086600000,
 "source": {"systeme": "AP",
            "db": "SQLSERVER_ASSUREPLUS",
            "table": "AP_USERS"},
 "key": "AP-5001",
 "after": {"AP_USER_ID": 5001,
           "AP_FULL_NAME": "DUPONT Marie",
           "AP_BIRTH_DATE": "12/04/1985", …}}

La clé de message est l’identifiant préfixé : toutes les versions d’une ligne vont dans la même partition, donc dans l’ordre. Les colonnes sont publiées brutes : le nettoyage est fait une seule fois, par Spark.

Arborescence HDFS

/datalake/fusion/
  bronze/src.ab.client/run=…/part-00000
  bronze/src.ap.paiement/run=…/…
  silver/client/       _SUCCESS, _schema.json
  silver/contrat/ sinistre/ paiement/

  silver/anomalie_qualite/ quarantaine/
  gold/dashboard.json
  gold/contrats_actifs_par_branche/
  gold/encaissements_mensuels/ …

Un lecteur ne consomme qu’un répertoire terminé (marqueur _SUCCESS, convention Hadoop) ; chaque écriture remplace sa partition, ce qui rend le traitement rejouable.

3. Exécution mesurée

Extraction complète des deux bases, puis publication sur Kafka :

L’exécution complète prend environ 15 secondes sur le jeu de test au 1/2 000e. L’exécution incrémentale suivante, sans nouvelle donnée, prend 5 secondes : elle ne republie qu’une ligne (la borne inclusive du filigrane d’AP_PAYMENTS), et le chargement idempotent l’absorbe. À l’échelle réelle, multiplier les volumes par 2 000 justifie Spark : le dédoublonnage compare 924 paires au lieu des 36 millions qu’impliquerait un produit cartésien, soit, en production, quelques millions de comparaisons au lieu de 1,4 × 1014.

Choix de conception

  • Une couleur par source, toujours la même : brique pour AbAssurance, ocre pour AssurePlus, prune pour les clients communs. La palette a été validée par script : contraste suffisant, distinction pour les trois formes de daltonisme, en thème clair comme en sombre. Un filtre « Source affichée » masque une série sans jamais recolorer l’autre.
  • Chaque graphique a une vue tableau (« Voir les données ») : lecture exacte, accessibilité aux lecteurs d’écran, copie dans un tableur.
  • Une carte en tuiles des régions plutôt qu’une carte géographique : chaque région a la même surface et reste lisible, même la Corse et l’Outre-mer.
  • Aucun script tiers : Chart.js est servi par l’application, et la politique de sécurité du contenu (CSP) interdit tout script ou style externe ou en ligne.

L’administrateur voit l’onglet « Qualité et exécution » (règles déclenchées, réconciliation, durée des étapes, relance du pipeline) et la file des paires de doublons nominatives.
