Question 2. Proposez un framework adapté (de préférence dans Python et des outils de data mapping et data migrations).

C3.2 — Critères : maîtrise du cadre de programmation ; cohérence de l’approche technologique au regard des objectifs.

1. Les besoins qui orientent le choix

  • Traiter des centaines de téraoctets (Oracle) et 17 millions de clients : le moteur doit être distribué.
  • S’intégrer à la chaîne imposée par la direction technique : Talend, Kafka, Hadoop, Spark.
  • Décrire le mapping de deux schémas hétérogènes de façon lisible par le métier et versionnée.
  • Migrer sans arrêter les applications historiques : coexistence, synchronisation continue, bascule progressive.
  • Préparer l’IA (énoncé) : l’écosystème doit être celui de la data science.

4. Le framework retenu : un noyau Python partagé par deux moteurs

Le choix central est de ne pas écrire les règles deux fois. Le paquet fusion contient tout ce qui relève du métier : nettoyage, mapping, règles de qualité, score de doublon. Deux moteurs l’exécutent :

  • le moteur local (Python standard) pour le poste du développeur, les tests et le serveur de démonstration. Le pipeline complet tourne en 15 secondes sur le jeu de test ;
  • les jobs PySpark (jobs/spark) pour le cluster. Ils distribuent les mêmes fonctions sur les partitions (mapPartitions, UDF) et n’ajoutent que ce que Spark fait mieux : lecture de Kafka, jointures distribuées, agrégats SQL, écriture Parquet sur HDFS.

Un test de la CI exécute les deux moteurs sur les mêmes événements et compare les résultats : mêmes volumes par table, mêmes orphelins, mêmes anomalies, mêmes contrats actifs par branche, mêmes paires de doublons. Si quelqu’un modifie une règle d’un côté seulement, la CI échoue.

Le mapping comme code

Extrait de fusion/mapping/mapping.toml. Chaque attribut cible déclare sa colonne dans chaque source, la chaîne de transformations et la règle métier qui la justifie :

[[contrat.champ]]
cible = "prime_annuelle"
type  = "DECIMAL(10,2)"
ab    = "AB_PRIME_ANNUELLE"
ap    = "AP_MONTHLY_PREMIUM"
t_ab  = ["montant", "prime_positive"]
t_ap  = ["montant", "mensuelle_vers_annuelle", "prime_positive"]
regle = "Unité commune : prime ANNUELLE. AP stocke une prime mensuelle, multipliée par 12. Prime ≤ 0 → NULL (DQ07)."

Au chargement, le moteur vérifie que chaque colonne existe dans le schéma source, que chaque transformation est connue et que la clé est mappée. Une faute de frappe est donc détectée avant tout traitement, pas au milieu de la nuit. Le même fichier produit talend/tmap_mapping.csv (python -m fusion mapping) pour le composant tMap des jobs Talend, et l’Annexe A de ce dossier.

5. Stratégie de migration

La migration suit une logique de coexistence puis de bascule progressive : les applications historiques restent en service pendant toute la transition, comme l’exige l’énoncé.

  1. Reprise initiale : extraction complète par lots (Talend ou fusion extract), chargement des zones bronze et silver, contrôle de réconciliation.
  2. Synchronisation continue : Debezium publie chaque modification sur les mêmes topics src.*. Le traitement silver étant idempotent, rejouer un message n’a aucun effet de bord.
  3. Double run : pendant plusieurs clôtures mensuelles, les reportings sont calculés par l’ancien et le nouveau système, puis comparés.
  4. Bascule par domaine (reporting, puis analyse des sinistres, puis relation client), chacune réversible tant que les bases historiques sont alimentées.
  5. Décommissionnement des flux historiques, les bases restant consultables pour les obligations réglementaires de conservation.
