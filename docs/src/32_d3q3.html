Question 3. Identifiez un bug potentiel dans le pipeline.

C3.3 — Critères : pratiques pour identifier la source des bogues, pour les corriger, pour tester et valider les correctifs.

Le bug présenté ici n’a pas été imaginé pour l’exercice : il a été rencontré pendant le développement, lors de la première exécution incrémentale. Il est caractéristique des pipelines Kafka, où la livraison est garantie au moins une fois et non exactement une fois. Il est suivi comme l’anomalie FUS-9.

1. Le symptôme

Première nuit : exécution complète, réconciliation exacte. Deuxième nuit : aucune donnée nouvelle dans les sources, et pourtant le pipeline s’arrête sur le contrôle de réconciliation :

$ python -m fusion run --complet        # nuit 1 : 15,4 s, réconciliation exacte
$ python -m fusion run                  # nuit 2 : aucune ligne nouvelle dans les sources
fusion.pipeline.ReconciliationError: réconciliation en échec :
  AB_CLIENT    lignes_source  6 000   lignes_silver  12 000   écart  +6 000
  AP_USERS     lignes_source  2 500   lignes_silver   5 000   écart  +2 500
  AB_CONTRAT   lignes_source  9 779   lignes_silver  19 558   écart  +9 779
  …            (les huit tables doublées)
  AP_PAYMENTS  lignes_source 50 736   lignes_silver 101 472   écart +50 736

Le garde-fou a joué son rôle : rien de faux n’a été publié. Mais le pipeline ne pouvait plus tourner deux nuits de suite, et la question restait entière : que se serait-il passé sans ce contrôle ?

2. Identifier la source

  1. Reproduire de façon déterministe. Les données de test étant générées avec une graine fixe, le scénario « exécution complète, puis incrémentale » reproduit l’erreur à l’identique sur le poste, à chaque fois. Un bug reproductible est à moitié résolu.
  2. Lire la forme de l’écart. Toutes les tables sont exactement doublées (+100 %). Ce n’est donc ni une règle de nettoyage, ni une jointure : toutes les lignes ont été chargées deux fois. Deux hypothèses restent : le bus a relivré des messages, ou l’extraction les a republiés.
  3. Suivre une ligne de bout en bout grâce au lignage. Le rapport d’exécution montre que l’extraction de la nuit 2 a publié 149 102 paiements : elle a tout republié. Le fichier des filigranes extract_state.json n’existe pas après la nuit 1. Première cause : en mode complet, run() passait state=None à l’extraction, qui ne mémorisait donc aucun filigrane.
  4. Se demander pourquoi une republication double les données. Une republication n’est pas une anomalie en soi : c’est un comportement normal d’un système « au moins une fois ». Deuxième cause, la vraie : le chargement silver faisait append. Il n’était pas idempotent.
  5. Chercher les autres déclencheurs de la même cause, au lieu de corriger seulement le cas observé :
    • la borne inclusive du filigrane d’AP_PAYMENTS (>= sur un horodatage, car la clé GUID n’est pas ordonnée) republie à chaque nuit les paiements de la dernière seconde lue ;
    • une relivraison Kafka : si le job s’arrête après l’écriture du silver mais avant la validation des offsets, tous les messages du lot sont relivrés ;
    • la mise à jour d’une ligne source (capturée par Debezium) ajouterait une seconde version au lieu de remplacer la première.

3. Mesurer l’impact sans garde-fou

Sur le chemin du moteur local, la clé primaire de l’entrepôt aurait arrêté le traitement : la nuit échoue, mais rien de faux n’est publié. Le chemin Spark, lui, calcule le gold directement depuis le silver Parquet, sans passer par l’entrepôt. J’ai mesuré ce qu’il aurait affiché (reports/bug/2-impact-sans-garde-fou.txt) :

C’est le pire type de bug pour un projet de fusion : aucun plantage, des chiffres plausibles, et des statistiques financières doublées présentées à la direction.

4. Corriger

Méthode : d’abord un test qui échoue, ensuite le correctif (règle du CONTRIBUTING.md). Sur la branche fix/FUS-9-paiements-comptes-deux-fois, le premier commit ajoute cinq tests de reproduction, un par déclencheur. Ils sont rouges :

FAILED tests/test_idempotence.py::test_rejeu_incremental_sans_nouvelle_donnee    ReconciliationError
FAILED tests/test_idempotence.py::test_mode_complet_enregistre_les_filigranes    FileNotFoundError
FAILED tests/test_idempotence.py::test_relivraison_apres_arret_avant_commit      15 048 lignes au lieu de 7 524
FAILED tests/test_idempotence.py::test_borne_inclusive_du_filigrane_ap_payments  assert 7525 == 7524
FAILED tests/test_idempotence.py::test_la_derniere_version_d_une_ligne_l_emporte assert 2 == 1
5 failed in 6.23s

Le second commit corrige la cause, pas seulement le symptôme :

Avant (ajout)

@dataclass
class SilverStore:
    tables: dict[str, list[dict]]

    def add(self, entite, record):
        self.tables[entite].append(record)

Après (upsert idempotent)

@dataclass
class SilverStore:
    rows: dict[str, dict[str, dict]]  # par identifiant

    def add(self, entite, record):
        uid = record[f"{entite}_uid"]
        previous = self.rows[entite].get(uid)
        if previous is not None:
            self.remplacements += 1
            for m in MARQUEURS:  # garde les contrôles posés
                if m in previous and m not in record:
                    record[m] = previous[m]
        self.rows[entite][uid] = record  # dernière version
  • Silver idempotent : indexé par identifiant, chaque réception remplace la version précédente. L’ordre est fiable, car une clé va toujours dans la même partition Kafka. Le même principe est appliqué dans le job Spark (fenêtre row_number() sur l’identifiant, offset décroissant).
  • Filigranes : le mode complet part d’un état vide mais l’enregistre.
  • Journal qualité : une anomalie est identifiée par (règle, source, entité, ligne). Une ligne republiée n’est plus signalée deux fois, sinon l’onglet qualité aurait lui aussi doublé.

5. Tester et valider le correctif

  1. Les tests de reproduction passent (5 sur 5), ainsi que toute la suite : aucune régression.
  2. Le scénario réel est rejoué (reports/bug/4-validation-correctif.txt) : la nuit 2 s’exécute en 5 secondes. L’extraction ne republie qu’une ligne (la borne inclusive), absorbée par l’upsert. La réconciliation est exacte et les indicateurs sont identiques à ceux de la nuit 1.
  3. La CI vérifie l’équivalence côté Spark : un test publie deux fois les mêmes événements et contrôle que le job Spark produit les mêmes volumes que le moteur local.
  4. Les tests restent dans la suite comme tests de non-régression. Ils documentent le comportement attendu mieux qu’un commentaire.
$ python -m fusion run --complet   →  15,7 s
$ python -m fusion run             →   5,0 s   republiées : {'AP_PAYMENTS': 1}   absorbées par l'upsert : 1
                                               réconciliation : OK   encaissé 12 mois : 8 579 860,23 €   contrats actifs : 9 402

L’historique Git garde la trace du raisonnement : b94e284 test(silver): reproduit le double comptage… puis 932f811 fix(silver): chargement idempotent…, fusionnés ensemble dans develop.

6. Prévenir

Ce bug enseigne une règle générale, désormais écrite dans le code : dans un pipeline alimenté par Kafka, tout consommateur doit être idempotent. La livraison exactement une fois n’est pas une propriété qu’on obtient gratuitement. Trois barrières se complètent : le traitement idempotent (qui corrige la cause), la réconciliation bloquante (qui détecte, et a détecté), et les contraintes de l’entrepôt (qui empêchent les données incohérentes d’entrer).
